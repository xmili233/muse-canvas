> **当前演示**：开启「引用画板」时，规则读取画板标题和文字类元素；分层组装与压缩为设计方案。

模型只能依据上下文做判断。本章决定模型每一步看到什么、按什么顺序排列、各占多少空间。

## 怎么设计

上下文按变化频率从低到高排列：

| 顺序 | 内容 | 何时变化 |
| --- | --- | --- |
| 1 | 系统说明：角色、画板规则、输出约定 | 版本更新 |
| 2 | 工具定义与 Skill 目录（仅名称和描述） | 版本更新 |
| 3 | 用户记忆摘要与当前画板记忆 | 偶尔 |
| 4 | 对话与工具记录 | 每步追加 |
| 5 | 画板快照与待办清单，附在最新一条消息后 | 每次请求 |

画板快照按与用户关注点的距离，逐级减少细节：

```text
<canvas board="Welcome" viewport="0,0 1440×900">
  <selected>
    n3 便签「这一页，留给细节」(0,510 300×194)
       一扇旧窗的比例 / 一段树影的留白 / 一句没来得及记下的话
  </selected>
  <visible>
    n1 图片「城市漫游 · 影像参考」(326,0 524×350) 蓝门、旧墙与晨光…
    n2 便签「把注意力还给街道」(326,376 296×200) 不设目的地，不赶时间…
    n4 色卡「雾蓝」#DCE4E7
    n5 文字「走慢一点，看见多一点。」
  </visible>
  <offscreen>
    下方：4 个元素（便签 3、图片 1），标题包括「路线」「咖啡店」
  </offscreen>
  <recent>用户刚刚选中 n3，并在下方新增 1 张图片</recent>
</canvas>
```

1. **稳定内容在前，变化内容在后**：系统说明、工具和 Skill 目录在一次对话中保持不变；画板快照放在最后。
2. **结构化文字为主，截图按需补充**：元素以文字结构描述；布局、配色等视觉任务再通过工具获取视口截图。
3. **由近及远逐级减少细节**：选中元素给出完整内容，视口内元素给出类型、位置和前几十个字，视口外只按区域汇总数量和标题。
4. **短编号与相对坐标**：元素使用本次对话内的短编号（n1、n2），坐标相对视口取整，由运行框架映射回真实 ID 和坐标。
5. **可恢复的压缩**：旧的画板快照和工具结果替换为一行说明；对话接近预算时压缩为摘要，摘要固定保留目标、已做的决定、用户否决的方向和未完成事项，原文仍可从事件记录读取。

## 为什么这样设计

### 1. 稳定内容在前，变化内容在后

模型服务会缓存相同的上下文前缀，命中缓存的部分更便宜、响应更快。Manus 认为缓存命中率是生产环境 Agent 最重要的指标，并建议前缀中不要放精确时间这类每次都变的内容。

同理，一次对话中不增删工具定义。需要限制某个工具时，由权限检查拒绝，而不是从列表中移除；否则缓存失效，前文提到的工具也会突然「不存在」，让模型困惑。

### 2. 结构化文字为主，截图按需补充

文字结构提供准确的 ID、内容和连线，适合引用和修改；截图提供疏密、对齐和整体风格，这些很难用列表表达。tldraw 的画布 Agent 同时使用两种表示，让模型「既理解视觉布局，也理解底层数据」。

截图占用的 token 远多于文字，所以只在任务与视觉相关时获取，不在每一步都附带。

### 3. 由近及远逐级减少细节

Chroma 的研究显示，即使任务难度不变，输入越长，模型表现越差；与问题相似但无关的内容尤其干扰判断。用户关注的地方给足细节，远处只保留「那里还有什么」，模型知道去哪里找，需要时再用工具读取。

### 4. 短编号与相对坐标

UUID 很长，占用 token，也容易被模型抄错。短编号更省、更准，运行框架负责映射，并校验模型给出的编号是否存在。取整后的相对坐标减少了无意义的数字，模型更擅长判断「在右侧」「在下方」这样的相对关系。

### 5. 可恢复的压缩

画板会变，旧快照留在上下文中只会误导模型，最新快照才是事实。工具结果也只在当时有用，事后保留一行说明即可，需要时可以重新读取。Manus 把这称为可恢复的压缩：去掉内容，保留找回内容的线索。

整段对话的摘要不可逆，最容易丢失的是约束，例如用户已经否决的方向。因此摘要按固定结构保留这些内容，而不是让模型自由概括。
